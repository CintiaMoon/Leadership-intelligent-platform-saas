## Phase 2 evidence (not tied to one AC)
- `TransferRules` (pure): refused-whatever-the-role, recipient eligibility, and the preconditions of completion in the order of the spec (`TransferRulesTest`, 9 tests).
- `OwnershipTransferService` (everything before any lock: outsider 404, early refusal of other roles, 404 for a non-recipient, recent authentication, the initiation limit read before and counted after the commit) and `OwnershipTransferTransactions` (initiate, cancel, accept, expire, deletion hook, reads; company row, then transfer, then the two memberships in ID order, loaded fresh by `lockLiveByCompanyIdAndUserIds`).
- `OwnershipTransferSweep` (hourly, `app.ownership.sweep-interval`): lists overdue pending transfers as plain values and expires each in its own transaction that locks the company first and re-checks.
- Four outbox event types with handlers (`OwnershipTransferEmails`), `AuthEmails.ownershipTransfer` (fixed subjects, the company name only in the body), `OwnershipConflictException` mapped to 409 `CONFLICT`.
- Mutation checks (each fails at least one test, each restored): demote and promote not flushed one at a time (4 tests); recipient eligibility not rechecked at acceptance; initiator need not still be the active Owner; an overdue transfer can be accepted; no early refusal before the locks (2 tests); the initiation allowance never counted; the old Owner's invitations not revoked; an overdue pending transfer blocks a new one; the recipient check removed in both layers. The recipient check removed in only one layer is not caught, by design: the service checks before the locks and the transaction checks again under them.
- **A test of mine was wrong, found by CI:** the first CI run of this phase failed `anAcceptanceRacingACancellationEndsInOneOfTwoSerialOrders` (581 of 582 passed). When the acceptance wins, the former Owner is already an Admin when the cancellation runs, so the cancellation is refused as forbidden (403, the early role check) or as not pending (409, the check under the lock), depending on timing; the test expected only 409. Both are the serial order "accept, then cancel". The test now accepts either. It passed 4 of 4 times in a row locally and once more alone; one further local run errored in all five tests after 752 seconds, which looks like the environment stalling (the same class that was suspected earlier) and was not investigated further.
- Test lesson: the test database is shared by every test, so the sweep also expires other tests' overdue transfers; the sweep tests look at their own transfers, not at a count.

## Phase 3 evidence (not tied to one AC)
- Contract first: five operations in `contracts/openapi.yaml` (`initiateOwnershipTransfer`, `getPendingOwnershipTransfer`, `getOwnershipTransfer`, `acceptOwnershipTransfer`, `cancelOwnershipTransfer`) and the schemas `InitiateOwnershipTransferRequest`, `OwnershipTransfer`, `OwnershipTransferStatus`; contract lint passes (2 warnings, not examined); `schema.d.ts` regenerated; web typecheck clean.
- `OwnershipTransferController` is thin (parses IDs, delegates, shapes the response); a missing or malformed `recipientMembershipId` in the body is a 400, a malformed ID in a path is a 404 (`PathIds`); acceptance rotates the session identifier after the commit (AC-AUTH-23, as leaving a company does); `OwnershipTransferResponse` has exactly the documented fields (no user ID, no address, no token; `resolvedAt` only once resolved); `SecurityConfig` lists the five routes explicitly and keeps `denyAll` for everything else.
- Postman: five requests after "Accept invitation", variables `recipientMembershipId` and `transferId`, collection name and description updated.
- Mutation checks (each caught by the tests named, each restored): session not rotated on acceptance (2 tests); the accept route not permitted by `SecurityConfig` (5 tests); `resolvedAt` returned as null before resolution (the exact-fields test).
- **Finding while testing, no code change needed:** a step-up replaces the session identifier, so a client must carry on with the new cookie and fetch a new CSRF token. The web client already does (the BFF passes `Set-Cookie` through and the CSRF token is fetched per call); the tests do the same.
- **Test infrastructure limit:** a session's age is measured from its real creation time but checked against the test clock, so moving the clock by days ends every session. The two HTTP tests that need an overdue transfer move the transfer's own timestamps back in the database instead; the 7-day clock tests are at the service level.
- **Two test mistakes found and fixed while writing them (not product faults):** an anonymous POST gets 403 `CSRF_REJECTED` before it can get 401 (the anonymous check now uses a GET), and a repeated acceptance must use the rotated cookie.
