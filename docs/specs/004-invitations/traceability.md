## Phase 5 findings and deviations
1. **The two 409 reasons share one message.** The design brief shows separate texts for "already a member" and "no room". The API answers both with `CONFLICT` and nothing that tells them apart, by design (Q-09, so that it does not reveal more than needed). The page therefore says "You can't join this company with this invitation. You may already be a member, or the company may have reached its member limit. Ask an administrator." If separate texts are wanted, the contract needs a stable reason code first; that is a change to approved behaviour and is not made here.
2. **A token in a query string reaches Spring Security's DEBUG line.** `FilterChainProxy` logs `Securing POST <path>?<query>` at DEBUG, so a client that put a token in the query string would have it quoted if that logger were raised to DEBUG. Our page and BFF never do this (the token is in the body), no Tomcat access log is configured, and no framework logger is raised outside the `com.example.saas` DEBUG setting of the local profile. The test pins the default levels and that the request logs nothing. Anything in front of the API (load balancer, CDN) that logs query strings would record such a request line; the runbook for the edge should say not to log the query string of `/api/v1/invitations/accept`. Not changed in code.
3. **After a new person verifies their address, the invitation is not carried automatically.** The verification link usually opens in a new tab (or another device), where the session storage of the first tab does not exist. The person then opens the invitation link from the email again (it stays valid until used or expired). In the same tab the token is kept and the flow works; the Playwright test covers that case. Carrying `next` through verification would need the verification page to know about the invitation and was not added.
4. **Running the end-to-end suite on this machine used the wrong database until overridden.** The git-ignored `application-local.yml` in `src/main/resources` is bundled in a locally built jar and fixes the datasource to the development database, so `DB_URL` from `playwright.config.ts` is ignored. CI does not have that file. The local run was done with `SPRING_APPLICATION_JSON` overriding the datasource (the E2E database on port 55432), the BFF credential, the signing keys and the public URL. A first attempt before the override failed at sign-up with 503 ("The service is busy") in every test that signs up, including the existing ones; I did not establish why (the API had connected to the development database, which held no `e2e.*` users afterwards), and with the override all 13 tests passed. Worth a line in the E2E runbook; not changed here.
